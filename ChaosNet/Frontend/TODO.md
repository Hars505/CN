# ChaosNet implementation outcomes

## Existing simulator to preserve

- [x] **Full operations dashboard** — Provide a responsive Cyber Cloud Network Operations Center dashboard with ChaosNet branding, WebSocket connection status (green when connected, red when disconnected), an LED-style tick counter, Play (`{"action":"start","tick_rate_hz":2.0}` or `POST /simulation/start`), Pause (`{"action":"pause"}` or `POST /simulation/pause`), Step (`{"action":"step"}` or `POST /simulation/step`), Reset (`{"action":"reset"}` or `POST /simulation/reset`), a 0.5–10 ticks/sec speed slider, and ROUND_ROBIN / LEAST_CONNECTIONS strategy selector.
- [x] **Full simulator VPC and node inspection** — Render VPC `10.0.0.0/16` as an interactive diagram with `igw-main`; AZs `us-east-1a` and `us-east-1b`; public subnets with `lb-a`, `nat-a`, `lb-b`, `nat-b`; private subnets with `router-a`, `app-a1`, `app-a2`, `db-primary-a`, `router-b`, `app-b1`, `app-b2`, `db-replica-b`; intra-AZ and cross-AZ links. Node/link status is UP/DEGRADED/DOWN with corresponding green/amber/red glow; primary DB has a gold crown badge and replica DB a silver badge. Show animated traffic particles on active request paths. Selecting a node opens details for latency, capacity and active connections, plus Kill Node and Spike Latency actions.
- [x] **Full simulator chaos studio** — Include target selector and duration slider in ticks with Inject for kill_node; kill entire `az-a` or `az-b`; crash/promote primary DB; sever cross-AZ links via network_partition; add +100ms latency spike to a selected node; inject 30% packet loss into a link; and manual recovery for a selected target. Submit documented `/chaos/{event_type}` REST bodies and/or WebSocket inject messages.
- [x] **Full simulator telemetry and terminal** — Show availability gauge `(successful / total) * 100`, mean failover duration in ticks (MTTR), average detection lag in ticks, requests lost during failover, healthy capacity versus total capacity, and average latency plus P95 latency over ticks. Stream/append a scrolling audit log with CHAOS purple, HEALTH amber, FAILOVER cyan, and TRAFFIC gray/green category badges, timestamps, event search and subsystem filter.
- [x] **Existing backend contract** — Connect REST base `http://127.0.0.1:8000` and WebSocket `ws://127.0.0.1:8000/ws`. Support `GET /topology`, `GET /metrics`, `POST /simulation/step`, `/simulation/start` with `{tick_rate_hz, requests_per_tick?}`, `/simulation/pause`, `/simulation/reset`, and `POST /chaos/{event_type}` for `kill_node`, `kill_az`, `drop_link`, `latency_spike`, `packet_loss`, `network_partition`, `db_primary_failure`, and `recover`. Handle `INITIAL_STATE`, `TICK_UPDATE`, control commands, connection lifecycle and reconnect behavior. Preserve this full dashboard at `/simulator`.

## Approved public experience

- [x] **Landing route, visual language and page structure** — Make `/` the public-facing “Failure, made visible” landing page and keep the existing full dashboard reachable at `/simulator`. Open with a live control-room scene rather than a generic marketing hero. Use left-aligned editorial copy beside a large live simulation canvas. Use midnight graphite `#10151C`, topology surface `#18232B`, primary text `#E8EEF2`, mint healthy/recovered `#65D6C2`, amber detected/degraded `#FFB454` and coral failure `#F06C5D`. Use Space Grotesk for headlines, IBM Plex Sans for explanations/metric labels and restrained monospace only inside event logs. Do not add generic gradient art, fake testimonials or a pricing section.
- [x] **Guided failure and recovery demo** — The primary CTA is “Run the failure demo”. The hero must explain ChaosNet immediately in plain language, show the real two-availability-zone topology, provide one guided scenario, and include Pause, Replay and “Open full simulator”. The sequence shows a healthy system with two availability zones, Zone A going offline, detection lag, traffic rerouting to the surviving zone, replica promotion, recovery without split-brain and final proof from measured results. Use the existing FastAPI/WebSocket API when reachable so captions follow real simulator behavior. If it cannot be reached, run an explicitly labeled deterministic local sequence; do not present local sample values as live backend measurements.
- [x] **Plain-language captions and technical details** — During the guided sequence present the captions “Zone A is offline”, “Health checks confirm the failure”, “Traffic is moving through Zone B”, “Replica promoted to primary” and “Service recovered” when supported by current scenario state. A “Show technical details” disclosure exposes each event type, tick number, target node and metric change without forcing all visitors to read implementation vocabulary.
- [x] **Proof, depth choices and closing CTA** — Include a “What ChaosNet proves” section covering that failure detection is not instantaneous, routing adapts to topology state, database failover avoids split-brain and recovery is measurable. Include engineering evidence only when verified: deterministic seeded runs, role-aware shortest-path routing, multi-AZ topology and the REST/WebSocket control surface may be described when the current code/backend demonstrates them. Do not state the attachment’s “44 automated tests across eight…” claim unless it is verified. Include “Choose your depth” paths to watch the demo, explore the architecture and run a scenario, followed by the CTA “Break the network. Understand the recovery.”
- [x] **Route manifest and landing-page metadata** — Keep `public/manus-routes.json` synchronized with `/` and `/simulator`. Give the landing page a meaningful title, description, initial content and share metadata; do not invent an absolute canonical/public origin that has not been configured.

The supplied backend at `127.0.0.1:8000` could not be reached from the sandbox during the initial build. That does not block implementation: the approved landing page must visibly distinguish live API operation from local deterministic demo mode.
